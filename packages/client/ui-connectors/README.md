# @deepseek-ai/dsh-client-ui-connectors

English | [中文](README.zh.md)

The connectors surfaces: the connected-providers list the [sidebar](../ui-sidebar/README.md) renders on its `connectors` tab, and the browse directory the [layout](../ui-layout/README.md) seats as a full-column overlay of the center area. One plugin owns both: the same `apply` closure registers the list into the shell-declared `sidebar.connectors` hole and the directory into the frame-declared `main.connectors` hole, and both registrants share the one controller the closure holds.

The list is the compact side: one row per **connected** provider (state dot + name, a `Custom` badge on user-authored rows), each row a button whose click — or Enter — selects the provider in the shared controller; the rail renders one link icon that requests expansion. It holds no tab state of its own (the shell renders it only on that tab) and reads the roster on mount.

The directory is the full column: a header with **New connector** (a form over the `AddCustomSpec` fields — name, optional id, stdio command/args or streamable-http url, optional token variable — whose save is `connector.add`) and a card per connectable provider. Each card shows the derived state, the connector's description, the risk notes derived client-side from the secret-free view (the token reference a connect depends on and can lose, the browser sign-in or device code whose grant can expire, the unmounted servers, the custom connector's reachability — three lines most actionable first), the server mount summary, and the state-following actions: an unconfigured token method offers **Configure** (the token dialog, whose save is `connector.configure` — the only place a credential value enters the client), a configured or failed connector offers **Connect** (token mode through `connector.connect`, an OAuth method through `connector.authorize`, a device method through `connector.deviceLogin`; a browser flow opens the returned URL or device page in a new tab), and a live mount offers **Disconnect** (`connector.disconnect`). Custom cards also offer **Remove** (`connector.remove`). The roster arrives through the `connector.list` wire verb as secret-free `ConnectorView`s — no server command, URL, header, or credential crosses the wire — and the cards read the same store as the list.

Clicking a card selects the provider and the directory switches to its detail: a connected provider lists its own chats — the sessions the session feed marks with the provider's `presetId`, blank entries hidden, latest first — each row opening that session in the conversation area, and **New chat** minting one under the same preset (`session.create` with the provider's `agentPreset`, then open); a not-yet-connected provider keeps the placeholder until its first session exists. **Back** returns to the card grid. The detail's session callbacks (`openSession`/`newProviderChat`) forward into the runtime's session service; the provider preset id itself resolves from the roster copy. The detail is those chats' only home in the sidebar: `apply` publishes the roster's preset ids under the `connectorPresetIds` ctx service — a bare snapshot store republished only when the id set itself moves — and the [ui-workspace](../ui-workspace/README.md) Chats tab and its search keep sessions running on those presets out of their rows, no matter which surface loads first.

Mutations adopt the response's updated view into the local roster — the response is authoritative, so no re-list follows, except `add`/`remove` whose responses carry no view and re-list instead — and a card-level failure renders under its card until the next operation on it. The shared controller single-flights the roster read: both surfaces call `load` on mount, and the second caller joins the first's in-flight read. The controller is the `apply` closure's: the roster snapshot (a `createSnapshotStore` the renderer binds to `useConnectors` through the inject `hooks` compartment) plus the mutation methods, which the registrants reach as plain injected callbacks. Re-mounting either surface (a tab switch off `connectors` unmounts the overlay) re-reads the roster, so the view is as fresh as the host, and the apply-closure controller outlives the overlay.

`ConnectedProvidersListProps` composes the `sidebar.connectors` owner share, the `connectors` locale namespace, and the list inject face (the `hooks.connectors` store binding plus `load`/`selectProvider`). `ConnectorsDirectoryProps` composes the `main.connectors` owner share, the same locale namespace, and the directory inject face (the store binding plus `load`/`openTokenDialog`/`setDialogDraft`/`closeDialog`/`saveToken`/`connect`/`authorize`/`deviceLogin`/`disconnect`/`selectProvider`/`openCustomDialog`/`setCustomDraft`/`closeCustomDialog`/`saveCustom`/`removeCustom`/`openSession`/`newProviderChat`), over which the global standard hooks already carry `useSessions` for the detail's chat list.

The `/client` exports are the plugin body (`apply`/`inject`), both faces' contract types, the controller class and its state types, and the locale key union; the registrant components, their sub-views, the risk-note derivation, and the CSS modules remain package-internal behind the slot registration.

## Model Experience

None, as the surfaces render host-derived connector views; nothing here reaches a model request. The token the dialog sends is stored host-side under the connector's credential reference and is never echoed back across the wire.

#### KV Cache effect

None; this package neither assembles nor sends a provider request.

## Known Limitations and Deferred Work

- **OAuth and device flows settle server-side** — `connector.authorize` and `connector.deviceLogin` start the flow and return; the cards show the row's `authorizing` state while the verify poll runs on the host and the roster re-reads on the next mount.
- **No wire push for state changes** — the roster re-reads on surface mount and after each mutation; a background connector failure surfaces on the next visit to the tab.
- **The custom form covers the single-server case** — the `AddCustomSpec` behind `connector.add` carries one server and at most one token method per connector; multi-server or custom deployments without a token still need a hand-written manifest.
