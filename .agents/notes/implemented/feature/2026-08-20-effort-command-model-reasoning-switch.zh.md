# Agent Note: `/effort` —— 切换会话模型的推理强度

Status: implemented

[English](2026-08-20-effort-command-model-reasoning-switch.md) | 中文

## 问题

会话的推理强度此前只能通过模型选择界面间接修改：composer 触发器里的 Effort 菜单，或选择新模型时被默认强度覆盖。用户没有一条面向文本的路径来查看当前生效的推理强度、支持的等级集合，或在它们之间切换——而强度恰恰是直接影响请求行为与成本的旋钮。

## 决策

网关（`createApiProxy`）在组合了命令注册表时注册宿主命令 `effort`：

- 裸形式 `/effort` 报告生效的推理强度（选择上记录的，否则模型默认，否则提供方默认）与支持集合。
- 带参数形式 `/effort <level>` 按 id 精确匹配、或按名称忽略大小写匹配当前模型的已公布等级，然后经由与 `selectModel` RPC 相同的 `ctx.llm.resolveCallConfig` 解析：不受支持的等级在调用提供方之前即以适配器自己的 `UNSUPPORTED_REASONING_EFFORT` 文案拒绝。随后以与 RPC 完全相同的方式更新进程本地选择，并经同一 `saveDefaultModelSelection` 接口保存部署默认值（保存失败同样只记日志）。

与 `/mode` 命令有两处刻意的不对称：

**不设忙闸门。** preset 重组合是结构性的——它在轮次运行期间重连 agent 的组合；而强度变更是请求头状态，只在下一次组装的请求生效。`selectModel` 本就可切换运行中的会话，`/effort` 沿用其先例，而不是发明第二条规则。

**客户端弹层是装饰（decoration），不是贡献项（contribution）。** `ui-model-selection` 对宿主命令做装饰：裸调用打开一个列出当前模型已公布推理强度的弹层（只有当模型未指定默认强度时才有 `Default` 行），带参数的行仍归宿主命令认领。弹层经由同一条 `selectModel` wire 行提交，因此命令与弹层是同一写路径的两个输入面，而不是两条写路径。

## 曾考虑的替代方案

- **专用的 `session.setEffort` RPC。** 否决。`selectModel` 本就接受包含强度的完整选择，并拥有其校验与默认值持久化；为一个它已经承载的值再开一条 RPC 会把两份职责分叉。
- **纯客户端命令贡献项。** 否决。强度是由 Host 拥有的模型请求状态；纯客户端入口会让文本路径（`/effort <level>`）无人处理，并让任何组合了命令注册表的非 Web 表面无东西可展示。
- **`/mode` 式的忙闸门。** 否决，属虚构约束：`/mode` 所防护的那一个在途竞态（重组合与运行中的组合相撞）对请求头值并不存在——运行中的步骤不会重读它。

## 后果

- 只有 Web 表面有 `/effort`：注册要求组合了命令注册表，而 CLI 不组合它。强度仍可在它原本可设置的每个入口设置；没有其他表面获得新入口。
- "模型可见 ⟺ 已记录"规则成立：强度只通过消费它的那个轮次所记录的 `request/header` 到达提供方请求；命令本身只记录标准的 `command/run`/`command/done` 生命周期事件对，不带任何选择载荷。
- 生效强度报告在调用时读取实时元数据（`resolveModelInfo`），因此命令能看到晚于目录加载的目录变更，无需任何刷新。
